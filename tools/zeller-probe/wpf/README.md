# Zeller WPF 内技术验证程序

Zeller 接入第 2 阶段的第一步。第 0 阶段的验证程序（`../dotnet`）是 WinForms，这个程序把同一个 SDK 放进 WPF 进程，回答第 0 阶段没覆盖的问题。它独立于收银系统，不读写收银数据库，不在 `hbpos_win.slnx` 里，CI 不编译它。

> **扣款是真钱。** 不刷卡的场景不花钱；要刷卡的场景金额是 $1，做完可以用程序里的退款按钮退掉。

## 运行

包源凭据的设置方法见 `../README.md`。SDK 包已在本机缓存时不需要凭据。

```powershell
cd tools\zeller-probe\wpf
dotnet run
```

命令行参数：

- `--windowed`：以普通窗口启动。默认是收银端模式（最大化、无边框）。
- `--auto-init`：启动后自动执行一次初始化。
- `--query <reference>`：可重复，启动后依次按 reference 查询，用来核实上一次运行留下的交易。

记录写在 `%LOCALAPPDATA%\HbZellerWpfSpike\`：

- `zeller-probe-journal.jsonl`：每次调用的「调用前」和「结果」。
- `zeller-probe-log.jsonl`：界面日志，含 `[窗口]`、`[看门狗]` 两类诊断行。
- `zeller-sdk.log`：SDK 自己的诊断日志（通过 `Terminal.LoggerFactory` 接出）。

## 和第 0 阶段程序的区别

- 宿主是 WPF，引用和收银端相同版本的 `Microsoft.Extensions.Hosting`，可以切到和收银端一样的最大化、无边框窗口，并能模拟扫码时的抢焦点（与 `MainWindow.ActivateForScannerInput` 相同的动作）。
- **严格串行**（默认勾选）：有调用没返回时不发新调用。取消勾选可以故意重现 SDK 的并发缺陷。
- **看门狗**：扣款超时后先 `cancel()`，等 3 秒；仍不返回就作废这次调用，重建 `Terminal`，再按 reference 轮询，并继续旁观 SDK 是否迟到返回。
- 可以作废并重建 `Terminal`，可以改应用名和版本号。
- 每 0.5 秒用 Win32 记录本进程里出现的其他顶层窗口（类名、位置、是否置顶、Owner）和前台窗口的变化。

## 结论（2026-11-05，SDK 0.1.0）

| 问题 | 结果 |
|---|---|
| SDK 能否在 WPF 的 UI 线程上工作 | 能。初始化 0.4–2.0 秒；扣款、查询、配对都正常 |
| 换程序、换路径、改版本号、改应用名之后是否仍已配对 | 是，不用重新配对，配对文件也没有被改写 |
| 重建 `Terminal` | 空闲时和有调用挂着时都只要 6–15 毫秒。新实例不用重新配对，不先初始化也能直接查询和扣款 |
| **扣款进行中再发起调用** | **新调用返回 `OperationBusy`，进行中的那笔结果丢失、永不返回。** 8 次全中（当天 6 次，第 0 阶段 2 次），没有反例。SDK 日志显示结果已收到，但没有交给等待它的调用 |
| 并发之后的调用 | 串线：扣款的事件发到查询调用上；一笔成交的结果被交给查询调用，查询报 `OperationResponseInvalid`（unhandled response type） |
| `cancel()` 的作用范围 | 不认调用。在已作废的调用上调 `cancel()`，被取消的是当时正在进行或下一个调用 |
| 断网且没有并发调用 | 扣款自己返回。网络一直断：`NetworkFailure`（44 秒、72 秒）。网络中途恢复：约 0.1 秒内返回 Approved 和完整小票（1 个样本） |
| 看门狗接手后的恢复 | 走通：`cancel()` 后 3 秒不返回 → 重建 → 新实例查询正常 → 下一笔扣款正常 |
| 无人值守（`unattended: true`） | 电脑上不弹窗口，没有 Try Again。提示刷卡后 30.1 秒返回 `InactivityTimeout` |
| 有人值守模式下的超时 | 扣款调用不返回，错误页等操作员。点 Try Again 在同一次调用、同一 reference 下重来 |
| SDK 窗口 | WinForms 窗口，1200×1020，自带置顶，有自己的 Owner。主窗口模拟扫码抢焦点后，键盘焦点在 1–2 秒内被抢走 |
| 已配对时调用 `setup()` | 约 8 秒返回成功，不改写配对文件，没有出现登录页 |
| 依赖版本冲突 | 没有。运行时 Logging.Abstractions 是 10.0，SDK 按 6.0.4 编译，调用正常 |

配对信息的位置：`C:\ProgramData\zeller-sdk\config.json` 和 `device.json`，是 DPAPI 加密文件，从文件头的标志位看是整机范围。登录页的 WebView2 数据在 `%LOCALAPPDATA%\zeller\payments-sdk\webview2`，按 Windows 用户分开。两处都不随程序的安装路径变化。

### 对第 0 阶段结论的更正

- 第 0 阶段两次「扣款调用一直不返回」的原因是并发调用，不是断网恢复的时机：那两次都在扣款进行中点过查询或轮询。所以 `../README.md` 里的 S8 和 S12 如果要重做，扣款返回之前不要点任何会调用 SDK 的按钮。
- 刷卡机的无操作超时固定约 30 秒。第 0 阶段的 42、34、60 秒，以及被拒结果晚 13 秒返回，多出来的是错误页等操作员的时间。
- Try Again 不会绕过程序，它在同一次调用里重来。
- `NetworkFailure` 不一定已扣款：两个样本，一次已扣，一次 0 笔。

## 重现关键场景

| 场景 | 操作 | 预期 |
|---|---|---|
| V1 并发丢结果（不花钱） | 取消勾选「启用看门狗」和「严格串行」，勾选「无人值守」。点「扣款」，出现 `AwaitingPaymentMethod` 后点一次「查询」。等 40 秒。再点「作废并重建 Terminal」「查询」 | 查询返回 `OperationBusy`；扣款不再返回；重建后查询正常，查到 0 笔 |
| V2 纯断网（$1） | 勾选「严格串行」和「无人值守」，不勾看门狗。点「扣款」，刷卡机提示刷卡时断开电脑网络，刷卡，等刷卡机显示成功，20–30 秒后恢复网络。期间什么都不点 | 网络恢复后扣款自己返回 Approved |
| V3 看门狗接手后重建（不花钱） | 勾选看门狗（总时长 40）和「看门狗接手后先重建 Terminal 再轮询」，取消勾选「严格串行」。点「扣款」，出现 `AwaitingPaymentMethod` 后点一次「查询」。等看门狗接手。之后勾选「严格串行」再扣款一次，在刷卡机上取消 | 看门狗接手、重建、轮询查到 0 笔；新实例上的扣款正常返回 `Cancelled` |

## 还没验证的

- 配对登录页在 WPF 进程里能否正常打字。要先解除配对才能测；打不了字时可以试「启用 WinForms 键盘互操作」。
- 换 Windows 用户之后是否仍已配对、是否要重新登录。
- 无人值守模式下需要签名或 PIN 的卡、被拒时的返回。
- 真正的 WPF 自动更新流程。目前是从「换路径、换版本号都保留」推断的。
- 触屏操作配对窗口。
