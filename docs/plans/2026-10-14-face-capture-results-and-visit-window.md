## 功能一：抓拍与比对结果（先做）

### 要解决的问题
- Match 模式处理完即删，看不到照片和比对分数，调参数、核对判定都没有依据。
- 名单命中后虽有通知（`FaceHitNotifier` → 通知平台 N1），但看不到「发给了谁、几个人已读」。
- 手机端没有通知收件箱，通知发出后无处查看。

### 范围
1. 主 API：只读的「抓拍与比对结果」列表与图片接口（后端已起草，见下）。
2. 复核任务列表补「命中通知发送情况」。
3. Web：`/system/face-match` 新增页签「抓拍与比对」+ 详情抽屉。
4. 手机：通知收件箱、抓拍与比对列表、详情（OTA；菜单由后端下发，须先 OTA 后部署后端）。

设计图：列表页签、详情抽屉、手机三屏（2026-10-14 已确认方向）。

### 数据来源与取舍
- 列表来自 Capture 模式留存的 `FaceCaptureEvent` 左连 `FaceMatchEvaluation`；Match 模式不留存，不会出现（名单命中仍在「复核任务」）。
- `FaceMatchTask` 与抓拍没有外键，按「同一摄像机 + 同一接收时间」对应（接收端建任务时用的就是抓拍的 `ReceivedAtUtc`）。
- `FaceMatchEvaluation.Decision`：0 NoMatch、1 Staff、2 RepeatVisitor、3 NewVisitor、4 LowQuality；没有评估行 = 未评估（开关未开、重复抓拍、接口失败）。
- `FaceCaptureEvent.MatchStatus` 从不更新，不能用来判断是否已比对。
- 通知发送情况回查 `AppNotification`（`DedupeKey = unwelcome-hit:{TaskId}`）与 `AppNotificationRecipient`：sent / pending / skipped，只显示人数与已读数，不显示姓名。

### 权限与隐私
- 复用 `FaceCapture.Images.View`，不新增权限码（避免权限入库 SQL 与移动端文案同步）；非管理员只看自己关联门店。
- 列表只返回图片编号，图片内容单独接口、服务端转发、每次查看写审计（沿用摄像机管理页的受保护读取）。
- 通知文案仍只用英文、不含姓名与照片；手机端点开后才按需加载照片，退到后台即丢弃、不落盘。

### 已完成（工作区，未提交）
- `FaceCaptureResultService`、`FaceHitNotifyLookup`、`FaceMatchScope`；`FaceMatchController` 新增 `GET results` 与 `GET results/{captureId}/images/{imageId}`；`FaceUnwelcomeTaskDto` 增加 `NotifyState / NotifiedAtUtc / NotifyRecipientCount / NotifyReadCount`；`GET config` 增加 `ResultsView` 标志。
- 尚未编译，尚无测试。

### 待办
1. 编译并补后端测试（列表过滤、门店范围、命中对应、通知状态、图片越权，SQLite 测试表需补 `Kind / PartIndex` 列）。
2. Web 页签与抽屉：服务层、类型、i18n（中英）、路由内页签可见性（`ResultsView`）、契约测试、包体预算检查。
3. 手机端：通知收件箱页（后端 `api/react/v1/notifications` 已有）、抓拍与比对两屏，按「移动端新增路由三端登记清单」登记。
4. 先把 1042 从 Match 切回 Capture（`EvaluateMatch=1`）才有数据可看——生产档案改动需单独授权。

### 风险

## 功能二：每店回头客窗口天数（后做）

### 目标
每家店可设置「回头客窗口天数」N：同一个人在 N 天内再次出现算回头客。默认 1（与现状完全一致，仍是「当天」）。

### 现状
- 访客库按「门店 + 营业日」一天一个（`v{门店}_{yyyyMMdd}`，`FaceVisitGroup`），删除时间固定为营业日次日 02:00。
- 所以现在「回头客」只表示同一天内再次出现；第二天同一个人会被当成新访客。
- 客流计数桶只有计数，不含身份，无法反推「某月有几个不同的人来过两次以上」。

### 设计：滚动窗口
- 每天仍建一个访客库；**搜索时同时搜最近 N 天的库**；新访客只写进当天的库。
- 每个库的删除时间 = 营业日后第 N 天凌晨 02:00（N=1 时即现在的次日 02:00）。
- 回头客 = N 天内再次出现；N=1 与现状一致。
- 不采用「一个月一个库」：会在月底出现边界断层，且要月底批量清理。

### 改动点
| 位置 | 改动 |
|---|---|
| `FaceStoreProfile` | 新增列「回头客窗口天数」，默认 1，迁移一条 |
| 接收端 `FaceMatchPipeline` | 搜索带上最近 N 天的库；建库时按 N 计算删除时间；`BusinessDayDeleteAfterUtc` 参数化 |
| 主 API 档案服务 | 保存时校验 1–30；N>1 时在合规记录里加「保留期限审查」警告项（只警告，不拦截，沿用 2026-10-13 的决定） |
| 主 API 到期清理 | 按每个库自己的 `DeleteAfterUtc` 删除（现有机制已按库记录删除时间，需确认无「次日」硬编码） |
| Web / 手机「人脸比对设置」 | 档案表单加天数输入，旁注「天数越长，保留的人脸特征越久」 |
| 审计 | 修改天数写入 `FaceAuditLog` |

### 取值与规则（建议）
- 默认 1，上限 30，超出不允许保存。
- 调小天数时，多出来的旧库提前清理，不等到期。
- 该店 N>1 且缺保留期限审查记录：档案页显示警告，功能照常运行。

### 开工前须核实
1. 腾讯云 `SearchFaces` 一次最多可带多少个库、多库搜索如何计费（影响 N 的上限和费用估算）。
2. 到期清理是否有「次日」硬编码；减天数时的提前清理是否会误删当天库。
3. `FaceTrafficBucket` 的回头计数在 N>1 后含义变化（「N 天内再次出现」），报表文案需同步。

### 二期（可选）：月度不同回头客人数
- 滚动窗口只能给出「回头次数」，要统计「这个月有几个不同的人来过两次以上」，需新增匿名「访客 ID × 到访日期」记录表（不存照片与特征）。
- 统计口径：回头客 = 同一访客在统计周期内出现在 2 个以上不同日期。
- 不在功能二范围内，等功能二上线、合规确认后再定。

## 上线前合规待确认（两个功能共用，须律师确认）
- 抓拍照片与比对结果的保留期限、谁能看（角色与门店范围）。
- 回头客窗口天数上限（建议 30）及对应的告示、员工知情、同意安排。
- 数据是否可送到境外处理：现网比对调用的是腾讯云广州节点（`iai.ap-guangzhou.tencentcloudapi.com`），澳洲门店人脸数据会出境，须一并确认。
- 说明：2026-10-13 已决定合规记录缺口只给警告、风险由用户承担，本节列的是仍需律师意见的事项，不代替律师意见。

## 顺序与发布
1. 功能一后端 → Web → 手机（OTA 先于后端部署，因为手机菜单由后端下发）。
2. 功能一稳定、合规方向明确后，再开功能二。
3. 两者均不改变现有 Match 模式「处理完即删」的默认行为；功能一的列表只展示 Capture 模式留存的数据。
